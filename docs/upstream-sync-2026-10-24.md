## 同步范围

本轮从 `maillab/cloud-mail` 合并到上游提交 `b5cbb98bb0c2f7090ea3187e3e7fe694190beea3`，包含 3.4.0 及后续更新，共 37 个上游提交。保留本分支域名、管理员、D1 / KV 绑定和独立维护文档。

主要变化：高级搜索、关键词高亮、主题与布局调整、分别发送、代发地址展示、邮件 HTML 清理、邀请码并发和有效期修复、统一 KV / R2 / S3 附件访问，以及 Turnstile 加载重试。

上游更换了截图文件格式和路径，本分支中英文 README 已同步使用新图片。

## 合并前的数据库准备

本轮新增 `email.sender_email` 字段。邮件写入和部分查询会使用它，**先准备数据库，再将升级代码发布到生产**。

1. 在 Cloudflare D1 中确认当前 Worker 的 `db` 绑定指向哪一个数据库。
2. 使用 D1 导出或可恢复的备份机制保留升级前数据与恢复点，不在公开仓库保存 SQL 数据备份。
3. 在目标数据库控制台执行只读检查：

   ```sql
   PRAGMA table_info('email');
   ```

4. 如果结果中没有 `sender_email`，执行上游 `v3_4DB` 中的同一条语句：

   ```sql
   ALTER TABLE email ADD COLUMN sender_email TEXT NOT NULL DEFAULT '';
   ```

5. 再次运行 `PRAGMA table_info('email');`，确认字段存在。若本来已有该字段，跳过 `ALTER TABLE`，不要重复执行或删表。
6. 确认主分支仍是本次准备的基线，再合并升级分支并检查部署结果。

这个字段是追加字段，默认空字符串；不会回填历史邮件的代发地址。旧代码不使用它，因此可以在旧代码仍运行时先添加。上游初始化接口也包含该迁移，但它只有在新代码部署后才能运行，且会执行其他初始化逻辑。本说明采用先检查、先备份、单独添加字段的顺序。

## 部署配置变化

- 本分支 `mail-worker/wrangler.toml` 的现有配置原样保留。
- GitHub Actions 的 Cloudflare 发信参数从 `CF_EMAIL` 改为 `EMAIL`。非空值会添加 `email` 绑定；使用 Resend 时保持该参数未设置，不要填写字符串 `false`。
- 使用 Workers Builds 的实例仍以 `wrangler.toml` 为准，不需要为了这次同步切换部署方式。
- 页面 URL 路径有调整，应从站点首页进入后再更新旧书签。

## 附件与文档变化

`/oss/*` 为统一对象存储入口，旧 `/static/*` 与 `/attachments/*` 路径也改为由统一存储服务处理。后台不再要求配置对象存储域名。存储优先级仍为完整 S3 配置、R2 绑定、KV；文件不会自动跨后端迁移。

## 部署后验证

按照 [验收清单](acceptance.md) 检查登录、邮件列表、详情、新收信、附件下载与已启用的外部发信，再验证搜索、主题和分别发送。

本地构建或打包通过不等于生产数据库已升级，也不等于站外投递成功。生产结果需单独记录。

## 回滚

保留升级前 Git 提交 `5d74d779a87f81d7978da623e4d514de785da0fa`。若需回退代码，在 GitHub 使用新的回退提交保留历史，并重新部署对应版本。

仅添加 `sender_email` 后，旧代码仍可继续使用原字段；代码回滚不需要删除新字段。数据库恢复应使用升级前备份或恢复点，根据实际故障决定，避免丢失升级后收到的新邮件。
